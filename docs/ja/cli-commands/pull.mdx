## 概要

`pull`コマンドは、NotCMSワークスペースへ登録されたデータベースから、設定済みの
TypeScriptスキーマを生成または更新します。

```bash
npx notcms pull
```

最初のpullは`init`が自動で実行します。データベースまたはプロパティを変更した後に、
この単独コマンドを実行してください。

## 実行内容

1. `NOTCMS_SECRET_KEY`と`NOTCMS_WORKSPACE_ID`を読み込み
2. NotCMSから現在のワークスペーススキーマを取得
3. 設定されたスキーマmoduleと`nc`クライアントを生成
4. 最初のデータベース用クエリを表示

## オプション

| オプション | 説明 | デフォルト |
| --- | --- | --- |
| `-e, --env <PATH>` | カンマ区切りの環境ファイルパス | `.env,.env.local,.dev.vars` |
| `--check` | ファイルを書き込まずスキーマが最新か確認 | `false` |

`--check`は生成ファイルが存在しない、または古い場合に終了コード1を返すため、
CI/CDで利用できます。

## 例

### スキーマを更新

```bash
npx notcms pull
```

### 独自の環境ファイルから認証情報を読み込む

```bash
npx notcms --env .env.development pull
```

### ファイルを書き込まず確認

```bash
npx notcms pull --check
```

## 生成されるスキーマ

型付きスキーマと、すぐ利用できるクライアントの両方を生成します：

```typescript
import { Client } from "notcms";
import type { Schema } from "notcms";

export const schema = {
  blog: {
    id: "abc123...",
    properties: {
      title: "title",
      content: "rich_text",
      published: "checkbox",
      publishDate: "date",
      author: "relation",
      tags: "multi_select",
    },
    options: { tags: ["AI", "Web"] },
  },
} as const satisfies Schema;

export const nc = new Client({ schema });
```

後から更新するためのpackage scriptも追加できます：

```json
{
  "scripts": {
    "schema:pull": "notcms pull"
  }
}
```

## スキーマ変更の概要

通常のpullは以前に生成されたスキーマと比較し、データベースの追加・削除、IDの変更、プロパティの追加・削除・型変更を表示します。ファイルがない場合や手動編集で対応外の形式になった場合は比較を省略し、既存スキーマを実行することはありません。`--check`はファイルを書き換えません。最新の場合は概要を省略し、未更新の場合は意味上の差分を表示します。

`pull --check` が未更新を検出した場合も、書き込まずに意味上の差分を表示します。初回取得と比較不能な既存ファイルは別々に案内します。比較時にローカルのモジュールは実行しません。

## 未対応のプロパティ型

<Note>
この動作は未リリースです。この変更を含むバージョンの公開後、プロジェクトの `notcms` 依存関係を更新し、同じバージョンに同梱されたCLIで未対応型を含むスキーマをpullしてください。旧SDKでは生成したスキーマの型検査に失敗し、旧CLIではスキーマ全体の取得に失敗する場合があります。
</Note>

`button`・`place`・`verification`や今後Notionに追加されるプロパティ型も、型名を保持します。`init`・`pull`・`pull --check` は対象のデータベース名・プロパティ名・型名を警告します。他のデータベースや対応済みの列は、従来の値・選択肢の型推論を維持したまま利用できます。`options` を含まない旧APIレスポンスにも対応します。

未対応型の値はTypeScriptの `unknown` 型となり、型付きの `where`・`sort` では利用できません。SDKはAPIの値を変換せず返しますが、値が返されたことやスキーマ取得の成功は、Notionから完全な値を取得できたことを保証しません。その列を利用する前に、サービスの同期診断を確認してください。

`pull --check` は引き続きスキーマの差分を判定します。未対応の型名が変わらなければ警告と終了コード0を返し、型名が変われば差分と終了コード1を返します。ファイルは書き換えません。

## 選択肢の型

CLIは `?include=options` を自動で指定して選択肢を取得します。旧CLIにはoptionsを含まないスキーマを返すため、生成したコードを旧SDKでも引き続き型検査できます。

データベースごとの任意フィールド `options` に、`select`・`status`・`multi_select` の選択肢名を保持します。`as const satisfies Schema` により、たとえば `options: { language: ["en", "ja"] }` のselect/statusは `"en" | "ja" | null`、multi-selectは `("en" | "ja")[] | null` になります。`where` の条件にも同じ選択肢が適用されます。

取得済みの空配列はselect/statusが `null`、multi-selectが `never[] | null` になります。`options` のない旧スキーマは従来の `string | null`／`string[] | null` を維持します。APIはメタデータ取得までoptionsを省略し、通常のDB同期またはサービス側のバックフィルで補完します。

Notionで選択肢を変更した後は、DBを同期してから `notcms pull` を再実行してください。選択肢の追加・削除やメタデータの取得状態の変化も差分に表示します。型はpull時点の内容を表し、SDKは実行時の未知の値を変換・破棄しません。
