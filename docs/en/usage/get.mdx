---
title: Fetch one page
description: Choose between a known page ID and a property-based lookup
---

Use `get` when you already have a page ID, and `getFirst` when you have a property
such as a slug. Both return the page's properties and Markdown `content`.
Database and property names below come from your generated schema.

## Fetch by ID

An ID identifies a particular page. Use it for links that should keep working
when a title or slug changes.

```ts
const [post, error] = await nc.query.blog.get("page-id-123");
if (error) throw error;
console.log(post.content);
```

If that page does not exist, `get` returns an error. The SDK does not turn it into
an empty page.

## Fetch by a property

A property lookup finds a page that matches your site's rule. For example, find
a published post by its slug:

{/* docs-check */}
```ts
import { nc } from "./notcms/schema";

const [post, error] = await nc.query.blog.getFirst({
  where: { slug: "hello-world", published: true },
});
if (error) throw error;
console.log(post?.content);
```

`post` is `null` when nothing matches. Your application can use that result to
show a 404. A failed request is an error, not a missing page.

<Note>
`getFirst` is available in NotCMS 0.5.0 and later. Upgrade the `notcms` package before using it.
</Note>

## Decide which match to use

`where` and `sort` work like [list()](/en/usage/list). If several pages match,
`getFirst` returns the first one in that order; it does not enforce uniqueness.

```ts
const [post, error] = await nc.query.blog.getFirst({
  where: { published: true },
  sort: { publishedAt: "desc" },
});
```

Use an explicit sort when “first” matters. For a slug route, keep slugs unique in
your content workflow, and manage redirects when they change. See the
[URL recipes](/en/examples/content-recipes) for language-specific slugs and ID fallbacks.

## Handle the result

| Outcome | `post` | `error` |
| --- | --- | --- |
| A page was fetched | Page with `properties` and `content` | `null` |
| No `getFirst` match | `null` | `null` |
| A request failed | `undefined` | `Error` |

Types are inferred from the generated schema. Check `error` before using the
page; for `getFirst`, also handle `null`. See [errors and rate limits](/en/usage/errors-and-rate-limits)
for retry decisions.

<Accordion title="Request and ordering details">
- `getFirst` sends one list request with `limit=1&include=content`, so only the first match and its content are transferred.
- Like `list`, `getFirst` returns content already synchronized into NotCMS. Unlike `get`, it does not contact Notion, so changes after the last synchronization, such as a page that is no longer accessible, appear after the next sync.
- With no sort, or when sort values tie, ordering uses registration order followed by page ID.
- The optional third tuple value is the list response on success or no match, or the failed response on error. It is `undefined` for a network failure. The SDK does not retry automatically.
</Accordion>

## Read saved page quality

<Note>
Unreleased: `quality()` is planned for `notcms 0.6.0`. It requires a server deployment that provides the page quality API.
</Note>

`quality(pageId)` reads the saved publication and latest synchronization attempt.
It does not fetch Notion or start synchronization, and it never falls back to `get`.
It returns the same `[data, error, response]` tuple as the other query methods.

{/* docs-check */}
```ts
import { nc } from "./notcms/schema";

const [quality, error] = await nc.query.blog.quality("page-id-123");
if (error) throw error;
console.log(quality.published?.content.completeness);
console.log(quality.published?.content.diagnostics);
console.log(quality.published?.media.status);
console.log(quality.latestAttempt?.report?.diagnostic);
```

`published` is `null` when no saved copy exists. `latestAttempt` can still describe
a failed first sync; it is `null` when there is no recorded attempt. An unfinished
attempt has `finishedAt: null` and `report: null`. Timestamps are ISO 8601 strings.

Properties and content each carry their own `version`, `completeness`,
`diagnostics`, and `media`. Locked dimensions can refer to different versions;
diagnostics describe the corresponding version, not necessarily the latest attempt.
Completeness is `unknown`, `complete`, `partial`, or `failed`. Media reports
`ready`, `pending`, `failed`, `unknown`, `unpersisted`, or `expired`, along with
`enumerated`, per-status `counts`, and fixed diagnostics. Unknown and legacy
measurements remain unknown, including zero media references without completed
enumeration. Media `ready` reflects stored upload results and current metadata;
this read does not check the object's live availability.

The exported `PageQuality`, `PageCopyQuality`, `DimensionQuality`, `MediaQuality`,
`PageSyncReport`, and `SyncDiagnostic` types describe the response. This method
requires an API deployment with the page quality endpoint; an HTTP error stays an
error tuple without an automatic retry or synchronization request.
