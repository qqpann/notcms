---
title: Astro integration
description: Choose when to fetch Notion content and how to turn it into pages
---

NotCMS supplies content; Astro decides when that content becomes HTML. Fetch from
Astro's server-side code, then pass the page data to your templates.

This guide assumes a generated `nc` client and a synchronized `blog` database.
The examples use `published` (Checkbox), `slug` (Text), and `cover` (Files & media).
Use your own database and property names.

For setup from a new project, use the [complete Astro example](https://github.com/qqpann/notcms/tree/main/examples/astro).
It includes schema generation, environment setup, and working list/detail pages.

## Choose when to fetch

| Approach | Choose it when | Content updates |
| --- | --- | --- |
| Static generation | A blog or documentation site can publish on a build cycle | Sync, then rebuild and deploy |
| On-demand rendering | Pages need fresh content on each request | Read the latest synchronized content at request time |

Both use the same SDK queries. Static generation needs credentials during the
build. On-demand rendering also needs them in the deployed server's runtime;
choose an [Astro adapter](https://docs.astro.build/en/guides/on-demand-rendering/) for that host.

Keep credentials on the server. The complete example loads the CLI's `.env.local`
for Node-based builds; see [Astro environment variables](https://docs.astro.build/en/guides/environment-variables/)
for other runtimes.

## Decide what to publish

Use a property such as `published` to express your site's publication rule:

```ts
const [posts, error] = await nc.query.blog.list({
  where: { published: true },
});
if (error) throw error;
```

Apply the same rule to lists and detail pages. A filter controls what your site
shows; it does not restrict what the workspace key can read. Synchronize only
content intended for that workspace's consumers. Media URLs are public.

## Turn content into routes

For a static site, use the published list to decide which pages exist. Astro's
`getStaticPaths` returns one route per page:

```ts
export async function getStaticPaths() {
  const [posts, error] = await nc.query.blog.list({ where: { published: true } });
  if (error) throw error;
  return posts.map((post) => ({ params: { id: post.id } }));
}
```

Inside `src/pages/blog/[id].astro`, use that ID to fetch the page and its body:

```ts
const [post, error] = await nc.query.blog.get(Astro.params.id!);
if (error) throw error;
```

Recheck publication before rendering the detail page: content can change between
the list and detail requests. In a static build, let an API failure stop the build
rather than publishing an incomplete site. Unpublishing also requires a fresh deployment.

For an on-demand slug route, use `findFirst({ where: { slug, published: true } })`.
Treat no match as a 404 and an API failure as a service error. Keep slugs unique
and manage redirects when they change. See [fetching one page](/en/usage/get) for
`findFirst` usage and release availability.

## Render the body and images

`post.content` contains Markdown. Choose a Markdown renderer for your site and
sanitize any HTML it produces. The complete example displays escaped text so
that content fetching can be tried without choosing a renderer.

A Files & media property contains image URLs. For example, render the first cover:

```astro
{post.properties.cover?.[0] && (
  <img src={post.properties.cover[0]} alt={post.title} />
)}
```

Use these URLs with Astro's image tools if you need optimization. Image processing
is a site-level choice; the SDK does not require a particular renderer or layout.

## Keep the schema current

After changing Notion properties, wait for synchronization, then run
`npx notcms pull` and review the generated types. [Schema checks in CI](/en/cli-commands/schema-ci)
help catch changes before the next deployment.
