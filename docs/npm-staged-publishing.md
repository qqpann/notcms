# npm staged publishing

`.github/workflows/publish.yml` keeps Changesets responsible for creating and updating the Version Packages pull request. After that pull request is merged, the workflow stages `notcms` with `npm stage publish` from `packages/notcms` when the push contains the package version and changelog update. The stage job makes this release decision before installing repository dependencies, so ordinary pushes do not execute package lifecycle scripts in the OIDC-enabled job.

The staging job uses npm trusted publishing through GitHub Actions OIDC. It has only `contents: read` and `id-token: write` permissions and does not read `NPM_TOKEN`. npm CLI 11.15.0 or newer and Node 22.14.0 or newer are required. For a release candidate, dependencies are installed with `--ignore-scripts`, the package is built and its SDK/CLI regression tests pass before staging, and both `npm pack --dry-run` and `npm stage publish` disable package lifecycle scripts. The workflow verifies every local file referenced by the package manifest, including runtime, CLI, and declaration entrypoints, and refuses unresolved `workspace:` runtime dependency ranges before staging.

Staging does not approve or publish the package, create a Git tag, create a GitHub Release, or update the `latest` dist-tag. A maintainer must review the staged package and approve it through npm with 2FA. The stage job does not use `npm stage list` or `npm stage view` because those review commands require npm user authentication and cannot run with this OIDC trust token. They do not require 2FA, but they are outside the trust relationship used for staging.

Before staging, the job performs a read-only `npm view` lookup. If the exact version is already published, the workflow reports a safe skip. A 404 from this lookup means that the version is not in the public registry and staging proceeds; a 404 from `npm stage publish` is treated as an error. An unpublished staged version cannot be discovered through the OIDC-only job, so an unapproved same-version stage remains an explicit failure requiring manual review. Recovery is manual review/approval or rejection in npm, followed by a rerun of the original failed workflow when appropriate; no `workflow_dispatch` recovery trigger is provided.

Before the first release, configure npm Trusted publishing for GitHub owner `qqpann`, repository `notcms`, workflow `publish.yml`, with stage-only permission. The pull request checks exercise decisions, package verification, and fixture failures; they do not submit a staged package or verify the live OIDC trust relationship. Review the first main release run separately and approve the staged artifact only after inspecting it.
